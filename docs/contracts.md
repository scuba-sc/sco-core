# Public service contract catalogue

The per-method machine authority is [`sdk/contracts/`](../sdk/contracts/).
It lives with SDK metadata rather than site content so downstream consumers share
one versioned format. This document's method cells are checked against those
records: update both together; CI refuses disagreement. Common reading rules,
per-service narrative and remaining gaps stay authoritative here and are carried
into the built catalogue, not copied into another editable prose source.
Which tables are Stable or Experimental across SDK 2.x, separately from
availability and evidence, is in [Stability](stability.md).

```sh
python3 tools/sdk_catalogue.py check
python3 tools/sdk_catalogue.py extract
python3 tools/sdk_catalogue.py build --out dist/sdk-catalogue.json --source-sha "$(git rev-parse HEAD)"
python3 tools/test_sdk_catalogue.py
```

Extraction requires Clang and an x64 C11 compiler environment. Clang's AST supplies
table membership and function types; compiled probes supply complete member
extents, sizes, service names and versions, reusing `tools/abi_snapshot.py` for the
frozen root table. The gate also compiles the C declarations printed in the rows.
No header or ABI pin is generated or changed. These checks prove inventory/layout
and source-backed language exposure, not runtime behavior or game verification.
The SDK profiles ship per-method records for their selected public headers: neutral
records with core, game records with game-sc, and both in combined or host-source
kits. Plugin kits place them under `contracts/`; source kits retain `sdk/contracts/`.
Repository-relative evidence and test references identify source context and are
not a guarantee that those paths are present in a kit. CI also publishes the built
catalogue as evidence.

### Machine format (schema 1)

The deterministic UTF-8 JSON has sorted keys, records sorted by stable `id`, no
timestamps or absolute paths, and an explicitly supplied full `source_sha`.
Top-level keys are `schema_version`, `sdk_version` (from `sdk/VERSION`),
`game_pack_version` (compiled `SCO_GAME_PACK_VERSION`), `source_sha`,
`contract_context`, `tables` and `records`.

- `contract_context`: `source` (`docs/contracts.md`), `reading_rules`,
  `entrypoint_context`, `remaining_gaps`; the prose is Markdown, with relative links
  interpreted against `source`.
- `tables`: object keyed by C table name. Each value has `source_header`,
  `version_macro`, `members` (header field order), `size` (x64 bytes), `version`
  (packed major/minor integer), `service` and `context` (service narrative).
- Each record has `id`, `kind`, `symbol`, `table`, `service`, `version_macro`,
  `source_header`, `signature`, `member_extent`, `table_size`, `since`, `purpose`,
  `buffer_contract`, `ownership`, `thread_affinity`, `callback_context`,
  `reentrancy`, `results`, `absent_capability`, `cleanup`, `language_mappings`,
  `examples`, `tests`, `limitations`. `table`, `member_extent` and `table_size`
  are null for entrypoints. Signatures are compiler-normalized C types; extents
  include the whole pointer. Preserve `id` across prose changes and symbol renames.
- `language_mappings` has `c`, `cpp`, `csharp`, `lua`; each has `status`
  (`direct`, `typed-wrapper`, `restricted`, `unsupported`) and nonempty `evidence`
  containing `{path, token}` source references. `restricted` means an exposed
  subset/adaptation, not unrestricted native access; read its source token and
  contract. Each mapping also has `tests`: paths drawn from the record's test
  inventory. A supported mapping requires nonempty language-specific tests; an
  unsupported mapping may use an empty list. C layout pins compile as C11 and
  C++20; C# and Lua must reference their own test suites. These are source links,
  not a recorded successful run or per-method runtime certification. Game mutations are unsupported in read-only Lua. A raw C# function
  pointer field is direct interop, not a typed wrapper.
- `examples` and `tests` contain repository-relative file paths; an empty examples
  list means none is identified, not proof that no example can exist. ABI test
  references are layout evidence, not semantic or live-game coverage. `limitations`
  contains explicit unestablished guarantees; `unspecified` never implies safety.

`extract` validates records and returns header-only `methods`, `tables` and
`game_pack_version` (without semantic contexts). `check` refuses inventory/type/
extent drift, duplicate IDs, missing paths, documentation drift and language
support claims without source evidence or language-specific tests. `build` validates before writing.


This catalogue covers the plain-C plugin boundary: every function-pointer **method** in
`sco_api` and every public service table declared by the top-level `include/*.h`
headers, plus the three native plugin entrypoints. It does not inventory data fields,
callback typedefs as independent methods, SDK wrappers, internal C++ classes or
product-link helpers under `include/sco/`. Wire-only helpers in `sc_ipc.h` and
`sc_net.h`, bridge layout headers, version constants and event payload structs have
no service tables and are excluded. Callback contracts are included with the method
that registers or invokes them. This scope is not a claim to cover every exported
symbol in a built binary.

The mechanically enumerated inventory is **215 table methods across 45 C table
representations, plus 3 plugin entrypoints: 218 method rows**. Multiple minor-version
representations can describe one service. The inventory below is the checklist;
each method has exactly one row in its table's section, in header field order.

Sources are the linked public headers, ABI layout pins, implementations and
[API reference](api-v1.md) / [game services](game-services.md). A source-described
contract is distinguished from an implementation observation. **Unspecified** means
no guarantee is established here; it is not permission to rely on observed behavior.
Game-service behavior has not been verified in a game session; see
[game service status](game/status.md). This document does not upgrade that status.

## Workflow language evidence and limits

The mappings describe individual primitives, not identical end-to-end language
surfaces. C++ actor/entity `Open` accepts a readable service prefix and guards each
method at the point of use; C# `Open` requires the complete 1.0 table before
opening. Neither `IsOpen`/Boolean conversion establishes operation capability.
For the bounded inspector, native C/C++ and C# can combine local-player,
health and entity-transform reads; Lua can use the read-only optional game
adapter. A zero health maximum is **unknown**. `Alive == false` is not proof of
removal: it also covers not-yet-streamed entities, missing capability and wrong
thread. Positions are zone-local metres; rotations are quaternion x/y/z/w.

Owned NPC creation/removal is **unsupported in Lua**. Scripts own no NPCs and do
not gain mutation by invoking a product command. DataCore's separate patch/write
service is not a game-object mutation binding. Native C++ may call the public C
`teleport.spatial` table; C# lacks that mapping. No wrapper is invented for parity.

The supported game-runtime target is **Windows x64**. macOS ARM64 and Linux runs
are development-fixture evidence; header cross-compilation to Windows x64 is
layout/compile evidence, not execution on Windows. C# layout/NativeAOT and real
host loading must run in their SDK CI jobs when `dotnet` is unavailable locally.
Complete combined game-workflow loading, delayed streaming/removal, provider
cleanup, and actual game semantics still require their corresponding host/game
acceptance. No simulator response certifies gameplay or arbitrary native-process
recovery. Provider reload refusal and retained raw-table lifetimes remain as
specified in the [lifetime audit](design/service-table-lifetime.md).

## Reading the rows

- Result names without the prefix mean the corresponding `SCO_*` value. Normal
  success is `SCO_OK` unless the row describes a Boolean, ID, count, string or void
  result. Listed failures are known cases, **not an exhaustive proof of every fault**;
  unspecified cases and precedence between simultaneous errors remain unspecified.
- The **size / since** cell gives the minimum x64 table byte extent that includes
  the *whole* function pointer, not just its first byte. Check `size >=
  offsetof(Table, method) + sizeof(table->method)` **before reading that pointer**,
  then check it is non-NULL. A version match alone does not justify reading an
  uncovered tail. The historical examples using `size > offsetof(...)` presume a
  well-formed complete provider table; current consumers must use the full extent
  and non-null method check, not that historical shorthand.
- For service discovery, `query_service` requires equal version majors and a
  provider minor at least the requested minor. Missing service: `SCO_NOT_FOUND`;
  incompatible/older version: `SCO_UNAVAILABLE`; output table NULL except on success.
  No missing pointer or service should be called. Tables may grow only by appending
  fields; unknown tails are not to be inspected. Host/game-owned tables outlive all
  plugins and are withdrawn after plugin unload. Third-party tables have the
  provider's lifetime, not that of the querying plugin.
- Caller size-prefixed inputs/outputs use `sizeof` as built by the caller. An
  oversized buffer/struct is not a promise that an unknown tail is initialized:
  **tail initialization and preservation are unspecified unless noted**. Command
  argument-definition stride is `arg_def_size`; `sco_arg` is frozen at 16 bytes,
  `sco_sql_value` at 16 bytes and `sc_vehicle_seat` at 96 bytes. Padding/reserved
  input fields are zero. Enums are 4 bytes; do not pass `_FORCE32` sentinels.
- **Byte handshake**: `*inout_size` is capacity on entry, bytes written on success,
  bytes needed with `SCO_TOO_MANY`; NULL output with zero capacity asks the size.
  Text is NUL-terminated and the terminator counts. This is not the same as
  `get_peers`' element-count handshake or the truncating fixed-capacity name calls.
  Required size may change between calls: retry if needed, not an atomic snapshot.
- Caller buffers stay caller-owned. No returned service pointer, string, mapping,
  command descriptor, frame or game ID is an allocation the plugin may free.
  “No allocation transfer” does **not** mean “no internal allocation” or “real-time
  safe.” Internal allocation bounds/latency are unspecified unless recorded.
- Unless a row says inputs are copied, their retention is **unspecified** beyond
  the synchronous call. Keep borrowed callback code and ctx alive for its registration
  or queued lifetime; ctx is not automatically freed. Callback payload pointers are
  valid during the callback only; copy retained data.
- Any-thread permission is not a recursive-reentrancy guarantee. Rows explicitly
  mark known callback-safe operations and otherwise say reentrancy unspecified.
  Game-thread permission does not permit calls from a game hook or arbitrary worker.
- “No cancellation entrypoint” records API surface, not guaranteed completion,
  rollback or an interruptible call. Unload/crash cleanup and callback quiescence
  are stated separately. Synchronous calls have no cancel token. Cancellation of
  an operation already in progress is unspecified unless stated.
- `last_error` is a diagnostic, not a return-value replacement: scope varies by
  service and another call may overwrite it. Complete diagnostics for every failure
  and error-text retention after success are unspecified unless documented.

## Native plugin entrypoints

Source: [`sco_api.h`](../include/sco_api.h),
[`loader.cpp`](../src/plugins/loader.cpp), [plugin exports](api-v1.md#the-plugins-exports).
All three are required for a native DLL. The loader contains faults in these exports;
this is containment, not memory safety or a sandbox. Query is called before load;
load is called after version checks. Shutdown delivery is best effort, not a
crash-safe persistence mechanism. Ordinary owner release runs resource hooks;
restart-required retained-provider faults skip them. An exposed provider whose load
returns non-OK may instead be refused with backing state retained; this is distinct
from a fault and does not run owner release or clear exports/module state.

## Host API: `sco_api`

Source: [`sco_api.h`](../include/sco_api.h), [implementation](../src/host/sco_host.cpp), [layout pin](../tests/abi_v1.c).

API 1.0 ends at 88 bytes; 1.1 adds the five final methods through 128 bytes.
`register_command` requires at least the 72-byte descriptor, at most 16 arguments,
non-NULL fn, and for nonempty defs `arg_def_size >= 24` and aligned to the argument
definition alignment. Copied strings have limits: name/title/capability 63 bytes,
help 255, argument name 31 and help 127, excluding NUL. Replies have a 256-byte
host buffer including NUL. Normal unloading removes owned registrations/queued
work; void methods silently ignore invalid self rather than returning BAD_ARG.
Source for registry/queue details: [commands](../src/api/sco_commands.cpp),
[events](../src/api/sco_events.cpp), [tasks](../src/api/sco_tasks.cpp),
[services](../src/api/sco_services.cpp), [raw handlers](../src/api/sco_raw.cpp).
The immediate invoke's “done once” rule applies after initial validation; invalid
self/name/count/buffer combinations can return without entering completion.

## sco.content: `sco_content_v1`

Source: [`sco_content.h`](../include/sco_content.h),
[implementation](../src/content/content.cpp), [layout pin](../tests/abi_content.c).
[G14 audit/design](design/content-access.md) records why the private index and
command registry were insufficient. This game-neutral service copies enabled
list/script pack bytes before consumer loads. Only startup snapshots are exposed;
no file paths or script execution. All calls require the game thread and live
self. Global limits: 4096 items, 16 MiB bytes; 1 MiB per file. A pack is refused

Size handshakes are binary: no appended NUL. Host restart invalidates old IDs.
C++ `scosdk/content.hpp` guards full extents/null pointers and failed reopen;
C#/Lua are not exposed. Synthetic kernel-only fixtures are not game evidence.
Script records cover `scripts/**/*.xml` and, on hosts after SDK 2.4 RC1,
`missions/<id>.scom` (1..100 lowercase ASCII letters, digits or underscores).
The latter fixes a product consumer namespace mismatch; RC1 does not discover it.
Opaque copied declarations require consumer format validation and a separate
mission ingest provider. Private `.cwmission` and rules remain unexposed.

## sco.ipc: `sco_ipc_v1`

Source: [`sco_ipc.h`](../include/sco_ipc.h), [implementation](../src/ipc/ipc.cpp), [layout pin](../tests/abi_ipc.c).

Channels are restricted to the caller's namespace. New Windows mappings receive
a DACL granting access only to the current user. Reused mappings are checked
for current-user ownership and sufficient size, not their existing DACL;
current-user-only access is therefore not guaranteed on reuse.
Bounds: 16 channels/plugin, 32 rings/channel, 4 KiB–256 MiB/channel, 512 MiB total
per plugin. Offsets exclude the first 64 header bytes; blocks align to 8 bytes,
rings to 64; ring data capacity is power-of-two, at least 64. Peer data is

BAD_ARG/MISMATCH to BAD_ARG; corrupt/epoch/busy/gone cases to FAILED. The header
says copy operations never block; the implementation still takes mutexes and
allocates staging buffers, so **no lock-free or bounded-latency guarantee** is
established. View access/close synchronization is the caller's responsibility;
its precise concurrency contract is unspecified. See [IPC](ipc.md).

## sco.widgets: `sco_widgets_v1`

Renderer-neutral retained panels, host-owned service 1.3. Source: `include/sco_widgets.h`,

the frozen sco_api ABI or the legacy sco.ui draw-context/hotkey route. Limits:
64 panels, 256 nodes/panel, 4096 live nodes, 256 items/node, 16 table columns.

methods/events are game-thread only. Events update retained state then dispatch
under the owner guard; replacing/removing a panel invalidates pending generations.
C is direct; C++ has `scosdk/widgets.hpp`; Lua has bounded `sco.widgets` tables
and registry-rooted typed callbacks. C# provides bounded typed nodes/events and

## Explicit remaining gaps

This is an inventory-complete catalogue, not a claim that the API has a complete
behavioral specification. In particular:

- Recursive reentrancy/depth, lock-acquisition latency, internal allocation bounds
  and worker-vs-unload quiescence are unspecified for most methods. Any-thread
  support alone does not establish them.
- There is no general cancel-token API or promise to interrupt running calls.
  Queue drop, registration withdrawal, rollback, deferred despawn and a game
  action's actual completion are different events; do not conflate them.
- No universal failure-output, tail-zeroing or diagnostic-isolation rule exists.
  Some methods zero outputs, some leave them unchanged, some change required
  sizes and some can fail after producing a game side effect. Buffer-specific
  conditions above take precedence over broad header prose.
- DataCore's allocation-exception translation, concurrent commits/discards on the
  same patch and ordering of competing saved-file commits are unspecified.
- spawn.entities failure-reason lifetime is unspecified; copy it during the call's
  immediate use and do not free it. Tracking failure may follow a successful spawn.
- game.vehicles / game.creative do not establish uniform released-self rejection
  or error-isolation guarantees; their last_error implementations need not enforce
  handle/service-start checks. Other game diagnostics also have no stopped-service
  refusal guarantee. Do not use stale handles merely because a table is still mapped.
- Direct IPC view synchronization with peers/close/unload is unspecified by this
  service table; a borrowed mapping does not grant safe concurrent unmapping.
- Watch/query-radius/state reserved behavior remains gated off; event vehicle-seat
  payload, actor health maximum and camera field of view are not filled from a
  verified live-game contract. Event payloads are not additional method rows;
  [game services](game-services.md#events) documents delivery and absent capability.

For additions, append a record under `sdk/contracts/` and update the corresponding
method row and inventory here. Run `tools/sdk_catalogue.py check` to compare both
with compiled header declarations and member extents. A comment, signature or
sibling service's behavior is not evidence for an unstated guarantee on a new method.
