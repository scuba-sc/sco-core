# Default availability and backend readiness

Reviewed 2026-10-25 against the public source at `4d05e738e88022a458e161a0abcd19b301d01889`, with SDK **2.4.0**, plugin ABI **1.1**, and game pack **0.8.0** as the compatibility baseline. This review identifies the work needed for comprehensive defaults. It records no new Windows, launcher, or game run and changes no capability, source flag, release approval, or provenance decision.

The published `sdk-v2.4.0-rc.1` source is `48d7055ef49e1b073ec59e4ce8ded7a6006329eb`. That archive snapshot, current source changes, and final release are separate. This document is a source review for the development branch, not a statement that published RC1 bytes include its changes.

## Implemented defaults in this development change

All fourteen read-only discovery/workflow tools are offered by default; the six-tool
profile is selected with `--minimal-tools`. Build/check execution is offered once
an operator configures project roots, retaining fixed commands and confinement.
`Platform::pluginsEnabled` now defaults true, but discovery still requires an
explicit nonempty `pluginRoot`; false retains the built-ins-only path. Tests cover
configured-root loading, explicit disable and empty-root behavior.

This review does not enable unfinished native methods or infer consent/quiescence.
Generic `gameServices` remains explicit because duplicate service names currently
stop composition partway while app startup continues; globally enabling it would
risk incomplete service publication. A complete game host must first establish
service ownership, adapters and admission. DataCore requires an applying adapter;
ImGui requires renderer integration; runtime inspection requires its independent
consent/offline/audit prerequisites described below.

The position-only relocation source extension was reviewed on 2026-10-26 against base `e75219bcdf856e3798ab9e99e26315041d14b6e1`; its separate OFF/synthetic row below adds no native activation.

## Reading availability correctly

[The status registry](../sdk/status_registry.json) contains **38 named capabilities whose recorded default is OFF**: 25 have `synthetic_only` evidence and 13 have `off_pending_probe` evidence. All 38 appear once in the inventories below. A registry entry records the reviewed availability/evidence baseline; actual host capability state is also computed from signatures, configured providers, admission, cleanup and fault state. The quantum path below already attempts production setup automatically under those conditions, despite its conservative OFF registry entry. Do not infer that changing a registry field changes runtime implementation.

[The roadmap](roadmap.md) separates contract, mock, static evidence, grounded native backend, game evidence and default-on behavior. Its post-2.4.0 work explicitly includes narrowed native rays, entity lookup, live GameRules values and audio. Comprehensive discovery should expose those contracts and their readiness honestly. Comprehensive behavior requires completing their adapters and acceptance work, rather than treating an unavailable response as a hidden switch.

The sources and tests linked here are public project material. Test links identify relevant verification work; they do not assert a fresh pass in this review. No proprietary executable, dump, address list, private analysis or player data is required to read this inventory.

## SDK-first work and acceptance handoff

Each resulting implementation task should name a roadmap milestone and the public contract/member/version it serves. Milestone 2 requires product features to be public-SDK consumers and studio mocks to implement the same tables. Milestone 3 requires native grounding and game evidence before its default-on stage. An agent should:

1. Pin the SDK archive/source, host/product revision, language and target toolchain independently.
2. Build the smallest author-owned plugin using public headers and matching contracts/catalogue; add a synthetic/mock case for each changed availability, size/version, lifetime and cleanup decision.
3. Record whether the work changes discovery, build inclusion, service publication, native readiness or actual gameplay behavior. Test each changed layer rather than using success in an earlier layer as proof of a later one.
4. For a native readiness change, retain the specific prerequisite from the table, the fail-closed/refusal cases, named Windows target evidence and separately recorded owner-run game observation. Missing game access leaves that gate open while supported SDK/mock work proceeds.
5. Update registry/docs/receipts from observed results and keep published RC bytes, development source and final release distinct.

This review's suggested next actions are comprehensive public discovery and workflow routing first; complete profile configuration and reproducible SDK-only consumer checks second; then prioritized native adapter/probe tasks with their existing safeguards and roadmap acceptance criteria. No capability listed above becomes implemented or game-verified merely because its interface is visible by default.
