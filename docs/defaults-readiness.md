# Default availability and backend readiness

This page says what is on by default in SDK **2.4.1** (plugin ABI **1.1**, game pack **0.8.1**), what each capability that is off needs before it can be turned on, and what the host, build and MCP defaults are. It records no run and changes no capability.

**Native game-service startup is on hold.** `Platform::gameServices` refuses app startup, so production does not publish the game tables today. The descriptions below are of retained implementation and contract intent, not of an enabled native path. [Game services](game-services.md) has the details.

## Reading availability correctly

[The status registry](../sdk/status_registry.json) records **41 capabilities whose default is OFF**: 28 have `synthetic_only` evidence and 13 have `off_pending_probe` evidence. [Status of every game.* table](game/status.md) lists every capability with its default and evidence; a capability with only synthetic or static evidence is marked "Not run in game." there. The tables below cover all 41 once, in three groups:

| Group | Capabilities | What decides it |
|---|---|---|
| [Opt-in native path](#opt-in-native-paths) | 7 | A native path exists. Configuration can select some of them today, but acceptance and lifetime requirements are open. |
| [Held for a named probe](#held-for-a-named-probe) | 12 | Rows resolve or a provider exists, but one observation in game has to settle a specific question first. |
| [No production backend yet](#no-production-backend-yet) | 22 | Needs an implementation, or lifetime or registration grounding, as well as a default decision. |

A registry entry records the reviewed availability and evidence. The actual capability state is also computed from signatures, configured providers, admission, cleanup and fault state, so changing a registry field does not change the runtime. The quantum path below already attempts production setup automatically under its conditions, despite its conservative OFF registry entry.

The [roadmap](roadmap.md) separates contract, mock, static evidence, grounded native backend, game evidence and default-on behavior. Turning a capability on takes the adapter and its acceptance work, not a hidden switch: an unavailable response is not a setting.

The next step for each is to run that probe on a named build, review the result, then update its proof attestation, the registry and the docs together. Do not set `probed` or a confirmation constant true to manufacture proof.

| `game.audio.triggers` | [audio service](../src/game/services/audio.cpp) starts with an empty [AudioBackend](../src/game/services/audio.h) in the [production composition](../src/game/services/spatial.cpp); synthetic owner, token and cleanup behavior exists. | A host-owned, isolated native effect provider with resolve, play and stop and lifetime and cleanup proof, then audible and native acceptance. ## Host, build, MCP and network defaults

These controls are separate from the 41 game capabilities. Build inclusion, tool discovery, executable access, service publication, privacy disclosure and gameplay activation are separate decisions.

| Control | Current default | Boundary to keep |
| --- | --- | --- |
| Star Citizen source build | `SCO_GAME_SC=ON` in [CMake](../CMakeLists.txt). Core-source archives omit the game pack and must configure OFF. | Keep the game pack in the complete host-source target and preserve the neutral core-source profile. A missing source component cannot be enabled by a build switch. |
| Retained widgets and ImGui renderer | `sco_widgets` is always built. `SCO_WIDGETS_IMGUI=OFF` controls the host-only ImGui adapter in [CMake](../CMakeLists.txt). | Enable the adapter only for a host profile that provides matching ImGui headers, implementation, linkage and renderer acceptance. The retained public API is available without it. |
| Runtime native peer build | `SCO_BUILD_RUNTIME_MCP=OFF` in [CMake](../CMakeLists.txt). The `core-source` and `host-source-sc` kits exclude the separately packaged runtime peer; enabling the option needs a full source checkout. | Building and packaging the peer is separate from connecting it. Including it by default needs platform build and packaging tests and provenance, and must not fabricate an adapter hash, credentials or host admission. |
| Plugin loading | `Platform::pluginsEnabled=true` ([app Platform](../include/sco/app.h)). Discovery needs a nonempty configured `pluginRoot`. Built-ins load regardless. Products can disable external discovery. | Keep owner disable markers, manifest and dependency checks and the product's chosen root. Never load code from an inferred working directory. |
| DataCore service publication | `Platform::dataCore=false`. It needs the host's applying CryPak and DataCore adapter and a data root. | Enable it for the complete admitted host composition once that lifecycle is configured; a neutral minimal host stays valid. Native live read and write readiness are separate. |
| Game-service publication | `Platform::gameServices=false`; requesting it refuses startup. | Keep unavailable until native execution and reader exclusion are proven, then resolve service-name ownership and validate the full lifecycle. |
| Reload copies | `Platform::loadFromCopies=false`; developer mode can map copied modules. | A developer host can default to copies if its filesystem, update and cleanup behavior is covered. This does not allow hot replacement of mapped native modules or fault recovery. |
| Public MCP discovery | The [SDK discovery server](../tools/sco-core-mcp/server.py) offers 15 read-only discovery and workflow tools by default: 6 catalogue tools, 7 extended tools including the static `get_service_status`, and 2 workflow tools. 13 are offered without a workflow index. `--minimal-tools` restores the original six catalogue tools. | Keep `--minimal-tools` for clients with old allowlists, and keep source and SDK metadata matched and retrieval bounded. No game attachment is needed. |
| Local MCP build and check | The three development tools are offered when at least one `--project-root` is configured. They run fixed programs with timeout and output bounds and process-tree termination. | Keep containment, fixed-command arguments and unavailable reasons when inputs or toolchains are missing. A catalogue connection never implies unrestricted filesystem execution. |
| Runtime inspection connection | [runtime launcher](../tools/sco-core-mcp-runtime/server.py), [host policy](../include/sco/diagnostics_policy.h): enable setting, model-disclosure consent, an exact six-tool allowlist, a pinned local adapter and credential, positive offline admission and a protected audit collector. Free-form disclosure is independent. | Make setup and readiness visible, but keep the evidence and configuration requirements. A compiled peer or a discoverable API cannot attest consent, a live audit collector, adapter identity or fresh offline status. [Runtime acceptance](runtime-acceptance.md) lists the missing Windows and manual evidence. |
| Private co-presence | [ControlPolicyV1](../include/sco/net/control.h) is enabled; the default bind and peers are loopback. Host and join need fresh local consent and session admission. | Do not widen network addresses, open sockets, store a passphrase or claim user consent as a side effect of tool discovery. |
