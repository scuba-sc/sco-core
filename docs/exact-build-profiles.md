# Exact-build candidate selection

The internal `src/game/exact_build_profile` code implements the v1 typed profile contract and a pure candidate selector. It is not a plugin API, native activation gate, executable reader, PE parser, or proof of compatibility. The production catalog and its compiled binding list are empty, so a well-formed observation always returns `UnknownExecutable`. No real game identity or table mapping is supplied.

The whole input catalog and binding list must be immutable for the duration of a call. Each profile has a unique ASCII ID, positive revision, lowercase 40-hex pack commit, named table set, and complete executable identity: lowercase SHA-256, nonzero file length, x64 PE machine, nonzero PE timestamp and image size, plus four uint32 manifest build parts. A compiled binding name maps to a nonzero code-owned handle. Both names and handles are unique. The selector validates the whole catalog and all bindings first, then requires the complete observed identity to match. Duplicate IDs, duplicate executable digests, invalid profiles, missing or ambiguous bindings, invalid observations, unknown digests, and mismatches refuse without a selection. It does not register or resolve signatures. An immutable handle only identifies a caller-owned binding; it does not establish that a binding or observation is authentic.

The typed interface does not accept JSON and is not a parser. The synthetic schema under `tests/fixtures/exact_build_profile` documents the proposed interchange structure, not an approved loader: any future parser must reject duplicate keys, unknown or missing fields, non-integer numeric forms, and values outside the specified ranges before constructing a profile. The canonical representation is ASCII JSON with recursively sorted keys, no whitespace or final newline, and decimal integers. It contains every profile field and no digest field. The test serializes the synthetic profile, compares the exact bytes to the shared fixture, and verifies its SHA-256. This digest identifies a definition; it does not authenticate it.

Before a real profile can be used, maintainers must independently review its source, the compiled table-set binding, and how the raw-file and manifest observations are bound to the actual mapped image, including mutation and lifetime races. Selection must precede construction and registration of a private complete table set; no mixing or timestamp-only fallback. Admission, owner retention and reader/worker drain remain separate prerequisites. A successful selection, static resolution, and actual game behavior are distinct evidence classes. None authorizes activation or weakens an existing refusal. No such mapped-image binding, profile-driven registration, or native runtime acceptance is implemented here.

The existing `RegisterGameSignatures` continues to register its legacy complete table set, and the frozen `game.build` v1 `pin_matches` remains timestamp-only. The selector does not change the 48-byte build value or any plugin ABI. No game binary or data pack was used for its tests.
